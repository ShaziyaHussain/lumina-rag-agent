# Lumina RAG Agent

Lumina is a browser-based document question-answering app built with React and Gemini. Upload text documents, ask questions about their contents, inspect the retrieved source passages, and copy assistant responses.

> **Prototype security note:** This Vite app calls Gemini from the browser. The configured API key is embedded in the client bundle, so it must not be treated as a protected secret or used this way for a public production deployment.

## The problem

Finding a specific answer in a collection of documents can mean repeatedly searching and reading long files. Lumina provides a simple chat interface that retrieves text passages relevant to a question and sends them to Gemini as context for a response.

## Features

- Upload multiple files through the browser interface.
- Split extracted text into overlapping chunks for retrieval.
- Rank chunks using an in-browser, TF-IDF-inspired keyword matching algorithm.
- Ask Gemini questions with the retrieved passages included as context.
- Inspect retrieved passages grouped by source document.
- Copy assistant responses to the clipboard.
- Remove uploaded documents from the current session.

## Technology

- **Language:** TypeScript
- **UI:** React 19
- **Development server and build:** Vite 6
- **Generative AI client:** Google GenAI SDK (`@google/genai`)
- **Styling and icons:** Tailwind CSS and Font Awesome loaded from CDNs

There is no application backend or database in the current implementation.

## Architecture and RAG workflow

```text
Browser file upload
        |
        v
App.tsx reads file text and stores documents in React state
        |
        v
utils/ragEngine.ts splits text into chunks
        |
        v
User asks a question
        |
        v
retrieveRelevantChunks ranks chunks by keyword matches
        |
        v
services/geminiService.ts sends the question and retrieved context to Gemini
        |
        v
ChatInterface displays the answer and expandable source passages
```

Document content, chunks, and chat messages are held in browser memory for the current page session. The app does not persist them to a database.

## How document processing and retrieval work

1. The upload handler reads selected files with the browser's `File.text()` API.
2. `createChunks` divides text into chunks of approximately 1,200 characters, with a 200-character overlap. It tries to end chunks near a newline or space.
3. When a question is submitted, `retrieveRelevantChunks` lowercases it, splits it into terms, and ignores terms of two characters or fewer.
4. For each chunk, whole-word occurrences add 5 points per match. If a term has no whole-word match but appears as a substring, it adds 1 point.
5. The app sends up to six of the highest-scoring chunks to Gemini. Chunks with no matching query terms are not included.
6. The returned source passages are displayed beneath the answer, grouped by document.

This is keyword-based retrieval—not vector search or embedding-based semantic retrieval. A relevant passage may be missed when it does not share useful keywords with the question.

## Source citations and copying answers

Assistant responses can show the passages retrieved for the question. Expand a document card to review its excerpts; the displayed excerpts are the retrieved chunks sent as context, not independently verified citations generated by the model.

Use **Copy answer** beneath an assistant response to copy its text. The interface shows confirmation when copying succeeds and an error message if the browser blocks clipboard access.

## Environment configuration

Copy `.env.example` to `.env.local` in the project root.

On Windows PowerShell:

```powershell
Copy-Item .env.example .env.local
```

Replace the placeholder with your own Gemini API key.

Vite reads `GEMINI_API_KEY` and maps it to the API key used by the Gemini client. Keep your real key in `.env.local`; do not commit or share that file.

> **Security:** Vite's current configuration injects this value into browser-side code. This is suitable only for local experimentation with a key you are willing to expose in the client. A production deployment should use a server-side design that keeps provider credentials out of the browser; that is not implemented in this repository.

## Testing

No automated test framework or test script is configured in `package.json`. Use the production build as a basic project check, then manually verify the app:

1. Start the development server and upload a `.txt` or `.md` file with content you can query.
2. Ask a question that includes terms appearing in the document.
3. Check that the answer appears and that its source card expands to show retrieved text.
4. Copy an assistant answer and paste it into another app.
5. Remove the uploaded document and confirm it disappears from the sidebar.

## Current limitations

- **PDF text extraction is not implemented.** Although the upload control lists `.pdf`, the app reads files using `File.text()`, which does not parse PDF documents. Use plain-text or Markdown files for reliable results.
- **Retrieval is keyword-based.** It does not use embeddings, a vector database, or semantic search.
- **Chat history is not sent to Gemini.** The service accepts a history argument, but the current request uses only the latest question and retrieved context.
- **Data is temporary.** Documents and messages are stored in React state and are lost when the page is refreshed.
- **The API key is client-side.** The current Vite configuration exposes the configured key in browser code; this is not a secure production architecture.
- **No automated tests are configured.**
- **File validation and upload error reporting are limited.** Upload processing errors are logged to the browser console.
